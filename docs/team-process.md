# 团队工作流程

版本 v1（2026-11-03 老板确认）。适用于本仓库全部开发与维护工作。

## 目的

在"让员工干活"和"省成本"之间定出可执行的规则：**按风险分级派活，只在该审查的地方审查；不为分工而分工。**

派发有固定开销——写清上下文、子代理重建上下文、往返确认。小任务派出去比主代理直接做完更贵，所以流程必须允许"不派"。

## 一、角色

| 角色 | 承担者 | 职责 | 硬边界 |
|---|---|---|---|
| 老板 | 用户 | 定目标、优先级、预算、拍板、授权发布 | 不参与执行细节 |
| 副总 | 主代理 | 拆解、定级、派单、验收、架构决策、汇报 | 不写业务代码；不可逆操作必自己做 |
| 主管 | standard / strong 档子代理 | 出方案、拆子任务、独立审查 | **不能派活**（平台不支持嵌套） |
| 员工 | light 档子代理 | 搜索定位、机械修改、跑现有测试、打包核验 | 不做架构判断 |

平台硬限制：

- 子代理不能嵌套派子代理；全局最多 5 个并发。
- 同一文件同一时间只能有一个代理写（派单时必须指定文件所有权）。

## 二、任务四级

定级由副总在动手前做，级决定流水线，不决定工作量。

| 级别 | 判定条件 | 流水线 | 审查 |
|---|---|---|---|
| **A 小改** | 单文件、<50 行、无架构影响、可回滚 | 派 1 名员工 → 副总验收 | 副总抽查 |
| **B 常规** | 单模块、验收标准可写成明确断言 | 派 1 名员工（light 或 standard）→ 副总验收 | 副总抽查关键点 |
| **C 有风险** | 跨文件、发布链路、数据契约、权限边界、可能不可逆 | 拆解 → 主管出方案 → 派员工实施 → 主管 Review → 副总终审 | 独立审查 |
| **D 疑难** | 跨条线重构、疑难排障、架构取舍、已多次失败 | 副总先只读定性 → 视情况派 strong 档 → 副总终审 | 必要时交叉验证 |

定级示例（取自真实经历）：

- 改一行 `.gitignore` 规则 → A
- `release.py` 的 stage 范围调整 → B（单文件、断言明确）
- 发布链路 + 文档口径 + 命名约定一起改 → C（跨文件、影响发布）
- 真机闪退定位、容器分层 FS 的 `.l2s` 载体问题 → D

## 三、什么时候副总自己动手

**必须自己做**：只读诊断、验收抽查、架构决策、发布 / 推送 / 删除等不可逆或共享状态操作、密钥与凭据。

**可以自己做（更省）**：总工作量小于派发开销时——一两行改动、一次查询、一次核对、强耦合的多文件小改。

其余一律派出去。

**透明机制**：副总决定自己做时，必须在同一句话里说明为什么没派。老板可随时驳回并要求派给员工。

## 四、派单六要素（缺一项不派）

1. **目标**：要达成什么，一句话说清
2. **已核实的事实**：路径、行号、已知结论，避免子代理重复探索
3. **输入输出**：读什么、产出什么、写到哪
4. **允许改动的范围**：明确文件/目录白名单
5. **验收标准**：可执行的检查命令或可观测结果
6. **禁止事项**：不许碰的路径、不许做的操作

另加**文件所有权**：多单并行时指定谁写哪个文件，避免冲突。

## 五、审查规范

独立审查只查三件事，不重做、不重跑全量测试：

1. **越界**：改动是否超出授权范围
2. **证据真实性**：是否只写"已验证"却不贴命令与输出
3. **新风险**：安全、兼容、副作用

副总终审在此基础上补：关键行抽查、跨条线影响、是否需要回滚方案。

## 六、省钱硬规则

1. **一次派完整**：任务描述给足上下文，不让子代理靠试错摸索。
2. **两次止损**：同一问题尝试 2 次未果立即停止，换方案或副总自己做，不允许第 3 次。
3. **不重复探索**：已核实的事实写进任务；子代理要求"再查一遍"时由副总判断必要性。
4. **档位就低**：能 light 不用 standard，能 standard 不用 strong。
5. **不汇报过程**：对老板只讲结论、证据、风险，不贴工作日志。

## 七、汇报节奏

- **派单时**：一句话——派了什么、谁做、产出是什么。
- **完成后**：结论 + 验收证据 + 风险与遗留。
- **要拍板时**：给选项 + 各自影响，不用开放式提问。

## 八、例外

- 紧急止血（派出去会误事）：副总可直接动手，事后补说明。
- 老板点名：按点名执行，不受分级限制。
